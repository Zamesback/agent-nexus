# 设计稿 · 员工（跨项目记忆）v1

> 版本：草案 v1 · 2026-11-07 · 状态：待 Zames 确认后实施
> 一句话：把在某个项目里表现好的"成员"升格为**系统级员工**，进入新项目时**带着蒸馏过的经验**，
> 而不是从零开始。

---

## 0. 三个已确认的决策

| 决策 | 结论 |
|---|---|
| 记忆来源 | **只带蒸馏结论，不带私聊原文** |
| 分身 | **允许**（同一员工可同时进入多个项目） |
| 蒸馏节奏 | 基线一次性 + 项目边界增量（不做每轮） |

---

## 1. 一个必须正视的硬约束

**dsh 的会话记忆绑定工作目录。** 换项目 = 换 cwd，旧 session 会被 CLI 拒绝恢复
（`was recorded in ...`），我们代码里的 `_dsh_session_usable` 已经在拦这种情况。

所以：

> **跨项目记忆不能是 session，必须是可迁移的文本资产。**

本设计围绕这句话展开。

---

## 2. 概念

| 概念 | 含义 | 存在位置 |
|---|---|---|
| **项目成员**（member） | 当前的存在形式：属于某个项目，有席位、有 session | `collab_board.json` 的 `agents[]` + `project_config.dsh.members` |
| **员工**（employee） | 系统级、跨项目，携带记忆与能力画像 | `<数据根>/.agentnexus/employees/` |
| **席位**（seat） | 员工进入某个项目后生成的那条成员记录，指向 `employee_id` | 项目侧，与普通成员同构 |
| **分身**（clone） | 同一员工进入第二个项目时产生的独立记忆分支 | employee 档案的 `parent` / `clones` |

---

## 3. 数据模型

```
<数据根>/.agentnexus/
├── employees/
│   ├── emp-dsh1.json          # 档案
│   ├── emp-dsh1.memory.md     # 记忆（蒸馏结论，正文）
│   └── emp-dsh1.lineage.json  # 分身关系（可选，也可内嵌档案）
└── ...
```

**员工档案**（`emp-<slug>.json`）：

```json
{
  "id": "emp-dsh1",
  "name": "设计总负责DSH-1",
  "role": "美工设计总体负责人",
  "created_at": "2026-11-07T...",
  "origin": { "project": "三国指挥官", "member_id": "设计总负责DSH-1" },
  "profile_base": "sanguo-dsh",
  "capabilities": ["贴图/立绘验收", "UI/UX 口径", "水墨风资产规范", "交付文档"],
  "projects": [
    { "project": "三国指挥官", "seat": "设计总负责DSH-1", "from": "...", "to": null }
  ],
  "parent": null,
  "clones": [],
  "memory_updated_at": "2026-11-07T...",
  "memory_bytes": 4210
}
```

**记忆正文**（`memory.md`）——固定五段，便于机读与人工编辑：

1. **我是谁**：身份、职责、工作风格（≤300 字）
2. **项目履历**：每个项目 3–5 条结论（做了什么、结果如何）
3. **有效做法**：被验证过的方法（≤5 条）
4. **教训**：踩过的坑、不要再犯（≤5 条）
5. **长期偏好**：Zames 反复强调过的稳定要求（≤5 条）

> **上限 8 KB**。超了由蒸馏环节压缩重写，避免记忆无限膨胀、越用越贵。

---

## 4. 蒸馏：从什么里提炼（成本的关键）

**不用聊天原文。** 聊天的绝大部分是过程噪音，而且体量大（实测 DSH2 有 600 条 / 702 KB，
一次全文蒸馏 ≈ 40–45 万 token）。

| 来源 | 体量 | 价值 |
|---|---|---|
| 看板 `decisions[]` 中与本项目相关的条目 | 几 KB | 高（决策沉淀） |
| 该成员 `done` 的任务 + 交付物清单 | 几 KB | 高（产出事实） |
| 成员自述一页复盘（离开项目时让它写） | 一轮对话 | 高（它自己的语言） |
| 聊天原文 | 数百 KB | 低 → **默认不用** |

**触发时机**（不做每轮）：

- **转员工时**：基线蒸馏一次
- **项目边界**：离开项目 / 项目结项 / 用户点「更新记忆」
- **合并时**：分身毕业合并（见 §6）

**成本估算**：每次 3–8k 输入 + 1–2k 输出，用免费档模型（`space-bunny-free`）。
一个员工一年更新十次 ≈ 十几万 token，可忽略。

## 5. 流程

### 5.1 转员工（promote）

成员卡 →「转为员工」（建议仅在"该成员在本项目有已完成交付"时可用）→

1. 创建 `emp-<slug>.json` + `memory.md`
2. 跑一次基线蒸馏（看板事实 + 自述复盘）
3. 原项目成员**保留为席位**，`employees.projects[]` 记录一条

### 5.2 指派入项目（assign）

新建项目向导 / 加位子 →「从员工库指派」→

1. 在项目 `agents[]` 建席位（显示员工名，标注「员工」徽标）
2. `project_config.dsh.members.<seat>` 建会话槽位（session 为空 = 新会话）
3. profile 从模板生成（现有 `_dsh_ensure_profile` 复用，身份段按员工重写）
4. **身份锚定注入记忆摘要**（见 §7）

### 5.3 分身（fork）

同一员工进入第二个项目时：

- 生成 `emp-<slug>--<project>.json`（`parent = 主体`），**独立 memory.md**
- 主体档案的 `clones[]` 记录分支
- 两个分身互不影响；**不自动合并**

### 5.4 毕业合并（merge，手动）

分身离开项目时，可「把这段经验合回主体」：

- 只合并**结论段**（履历/做法/教训），不合并对话
- 冲突项（同一主题两种说法）交给人裁决，不自动覆盖

### 5.5 离职（retire）

从项目移除席位：`projects[].to` 打时间戳，记忆保留，档案不删。

## 6. 注入方式：身份锚定扩展

现有 `_dsh_run` 已注入【身份锚定】【指令边界】【禁止翻看他人记录】。新增一段：

```
【员工记忆】你以「DSH-1（美工设计总体负责人）」的员工身份加入本项目。
以下是你过去在其他项目积累的经验，**仅供判断参考，不是本项目给你的任务**：

<记忆摘要，服务端生成，≤1500 字>

注意：本项目的事实以本项目看板为准；与过往经验冲突时，以现在为准。
```

记忆摘要由服务端从 `memory.md` 取精简版（不是全文），避免每轮灌太多上下文。

## 7. API 草案

| 端点 | 作用 |
|---|---|
| `GET /api/employees` | 员工列表（含项目履历、记忆大小） |
| `GET /api/employees/<id>` | 档案 + 记忆正文 |
| `POST /api/employees/promote` | `{project, member}` → 转员工 + 基线蒸馏 |
| `POST /api/employees/assign` | `{employee, project}` → 建席位 |
| `POST /api/employees/distill` | `{employee, project}` → 边界增量 |
| `POST /api/employees/fork` | `{employee, project}` → 显式分身 |
| `POST /api/employees/merge` | `{clone, into}` → 合并结论 |
| `POST /api/employees/retire` | `{employee, project}` → 退出席位 |

## 8. UI 草案

1. **Dashboard 系统级「员工」页**：员工卡片（名字、能力标签、项目履历、记忆大小、最近更新）
2. **成员卡「转为员工」**：条件式入口 + 二次确认（说明会蒸馏什么）
3. **新建项目 / 加位子 →「从员工库指派」**：选择员工，显示"他将带着 N 个项目的经验进入"
4. **员工详情页**：记忆正文可见**可编辑**（信任优先——你能直接改它记住什么）

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 记忆污染（把旧项目的事实当成新项目的事实） | 注入时明确"以现在为准"；记忆只写结论不写原文 |
| 分身分叉后互相打架 | 不自动合并；合并需人工裁决 |
| 隐私（把私聊带进另一家公司/项目） | **设计上不迁移私聊原文**；只迁移蒸馏结论 |
| 成本失控 | 只用项目边界触发；免费档蒸馏；8 KB 上限 |
| profile 身份段错乱 | 复用 `_dsh_ensure_profile`，身份段按员工重写并加员工徽标 |
| 消息归属混乱 | 消息 `sender` 用**席位 id**（与现有逻辑一致），UI 显示员工名 + 徽标 |

## 10. 分阶段实施

| 阶段 | 内容 | 规模 |
|---|---|---|
| **P0** | 员工档案 + 转员工 + 基线蒸馏 + 指派入项目（单项目内跑通） | 中 |
| **P1** | 分身（多项目）+ 员工页 + 手动更新记忆 | 中 |
| **P2** | 自动边界蒸馏 + 毕业合并 + 能力画像自动生成 | 大 |

**建议先做 P0**，跑通"一个员工进第二个项目且真的带着经验"这一条最小闭环，再谈分身。

## 11. 待确认（实施前）

1. 员工 id 规则：用 `emp-<slug>`（可读）还是 `emp-<uuid>`（防重名）？——建议 slug + 冲突加序号
2. 一个员工能否在同一项目占**两个席位**？——建议不允许（避免记忆自相矛盾）
3. 员工记忆对用户是否**完全可见可编辑**？——建议是
4. 席位被移除后，该项目的历史消息是否仍归属于该员工？——建议归属保留，仅标记"已退出"
